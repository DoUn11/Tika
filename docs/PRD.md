# Tika - 제품 요구사항 명세 (PRD.md)

> 상세 기능 명세는 [REQUIREMENTS.md](./REQUIREMENTS.md), 기술 상세는 [TRD.md](./TRD.md)를 참조한다.

## 1. 제품 개요

### 1.1 한 줄 정의

**Tika는 티켓 기반 칸반 보드 TODO 앱이다.**

### 1.2 배경

일반적인 체크리스트형 TODO 앱은 "할 일이 지금 어느 단계에 있는지"를 표현하지 못한다.
완료/미완료 두 가지 상태만으로는 *아직 손대지 않은 일*, *오늘 하기로 한 일*, *지금 진행 중인 일*을 구분할 수 없다.

Tika는 소프트웨어 개발에서 쓰이는 **티켓(Ticket)** 개념과 **칸반 보드**를 개인 할 일 관리에 도입한다.
할 일 하나가 티켓 한 장이 되고, 카드를 칼럼 사이로 옮기는 행위가 곧 상태 변경이 된다.

### 1.3 핵심 가치

| 가치 | 설명 |
|------|------|
| **한눈에 파악** | 모든 할 일이 상태별 칼럼에 분류되어 전체 현황을 즉시 인지한다 |
| **직관적 조작** | 드래그앤드롭으로 상태를 변경한다. 별도의 상태 선택 UI가 필요 없다 |
| **계획 대비 실적** | 계획한 일정(시작예정일/종료예정일)과 실제 일정(시작일/종료일)을 함께 기록한다 |
| **가벼운 시작** | 로그인 없이 접속 즉시 사용한다. 제목만 입력해도 티켓이 생성된다 |

### 1.4 타겟 사용자

- 개인 업무/학습 일정을 단계별로 관리하고 싶은 1인 사용자
- Jira, Trello 등 협업 도구가 과하다고 느끼지만 단순 체크리스트로는 부족한 사용자
- 계획한 일정과 실제 소요 시간의 차이를 추적하고 싶은 사용자

## 2. 목표 및 성공 지표

### 2.1 제품 목표

1. 할 일 등록부터 완료까지 전 과정을 **한 화면 안에서** 처리한다
2. 상태 변경에 필요한 조작을 **드래그 한 번**으로 끝낸다
3. 계획 일정과 실제 일정을 **자동으로** 기록하여 사용자 입력 부담을 최소화한다

### 2.2 성공 지표

| 지표 | 목표 |
|------|------|
| 티켓 생성 소요 시간 | 제목 입력 포함 5초 이내 |
| 보드 초기 로드 | 2초 이내 (NFR-001) |
| API 응답 시간 | 300ms 이내 p95 (NFR-001) |
| 상태 변경 체감 지연 | 0ms (낙관적 업데이트, NFR-004) |

## 3. MVP 범위

### 3.1 포함 범위

#### 3.1.1 단일 사용자

- 인증/로그인 없이 접속 즉시 사용한다
- 모든 티켓은 하나의 전역 보드에 속한다
- 사용자 구분, 소유권 개념이 존재하지 않는다

#### 3.1.2 고정 4칼럼

칼럼은 시스템이 고정 제공하며 사용자가 추가/삭제/이름 변경할 수 없다.

| 순서 | 칼럼 | 상태값 | 의미 |
|------|------|--------|------|
| 1 | Backlog | `BACKLOG` | 등록만 되고 아직 착수 계획이 없는 일 |
| 2 | TODO | `TODO` | 착수하기로 결정한 일 |
| 3 | In Progress | `IN_PROGRESS` | 현재 진행 중인 일 |
| 4 | Done | `DONE` | 완료된 일 |

**이동 제약**: 없다. 어떤 칼럼에서 어떤 칼럼으로든 이동할 수 있으며 역방향 이동도 허용한다.

#### 3.1.3 티켓 CRUD

| 기능 | 설명 |
|------|------|
| 생성 | 제목 필수. 설명/우선순위/시작예정일/종료예정일은 선택. 항상 Backlog 최상단에 추가 |
| 조회 | 보드 전체 조회(칼럼별 그룹화) + 개별 티켓 상세 조회 |
| 수정 | 제목, 설명, 우선순위, 시작예정일, 종료예정일을 부분 수정 |
| 삭제 | 확인 다이얼로그 후 영구 삭제(하드 삭제) |

#### 3.1.4 드래그 앤 드롭

- 카드를 다른 칼럼으로 드래그하여 상태를 변경한다
- 같은 칼럼 안에서 드래그하여 순서를 변경한다
- **낙관적 업데이트**: UI에 즉시 반영하고, API 실패 시 원래 위치로 롤백한다
- 순서는 `position` 값으로 관리하며, 카드 사이 삽입 시 `(prev + next) / 2`로 계산한다

#### 3.1.5 4개의 날짜 필드

Tika는 **계획**과 **실적**을 분리하여 기록한다.

| 개념 | 필드명 | 입력 방식 | 설정 시점 |
|------|--------|-----------|-----------|
| 시작예정일 | `plannedStartDate` | 사용자 직접 입력 | 티켓 생성/수정 시 |
| 시작일 | `startedAt` | **자동 기록** | TODO 칼럼으로 이동한 시각 |
| 종료예정일 | `dueDate` | 사용자 직접 입력 | 티켓 생성/수정 시 (오늘 이후만 허용) |
| 종료일 | `completedAt` | **자동 기록** | Done 칼럼으로 이동한 시각 |

**되돌림 규칙**:
- TODO → Backlog로 되돌리면 `startedAt`이 `null`로 초기화된다
- Done → 다른 칼럼으로 되돌리면 `completedAt`이 `null`로 초기화된다

**파생 규칙**:
- 오버듀 판정: `dueDate < 오늘 AND status ≠ DONE`인 티켓에 경고 표시를 노출한다
- Done 칼럼에는 `completedAt` 기준 **24시간 이내** 완료 티켓만 표시한다

#### 3.1.6 우선순위

`LOW`(회색) / `MEDIUM`(파란색, 기본값) / `HIGH`(빨간색) 3단계 뱃지로 표시한다.

### 3.2 MVP 완료 기준

- [ ] REQUIREMENTS.md의 FR-001 ~ FR-008이 모두 구현되어 있다
- [ ] US-001 ~ US-008의 인수 조건을 모두 충족한다
- [ ] TEST_CASES.md의 테스트가 모두 통과한다
- [ ] 모바일(360px) ~ 데스크톱(1024px) 반응형이 동작한다

## 4. 제외 범위 (2차 스펙)

아래 항목은 **MVP에서 구현하지 않는다.** 2차 스펙으로 분리한다.

| 제외 항목 | 제외 사유 | 2차 반영 시 영향 |
|-----------|-----------|------------------|
| **인증 / 로그인** | 단일 사용자 전제이므로 불필요. 인증 도입은 데이터 모델 전반에 소유권 개념을 추가해야 하는 큰 변경 | `tickets` 테이블에 `userId` 추가, 세션 미들웨어 필요 |
| **커스텀 칼럼** | 칼럼이 가변이 되면 상태값이 enum이 아닌 참조 관계가 되어 데이터 모델과 드래그 로직이 복잡해짐 | `columns` 테이블 신설, `status` enum → FK 전환 |
| **멀티 사용자 / 협업** | 담당자 지정, 실시간 동기화, 권한 관리가 함께 필요하여 MVP 범위를 크게 초과 | 실시간 동기화 계층(WebSocket 등) 필요 |
| **라벨 / 태그** | 필터링·검색 UI가 함께 필요하며 MVP의 핵심 흐름과 무관 | `labels` 테이블 및 N:M 관계 신설 |
| **코멘트** | 단일 사용자 환경에서는 협업 가치가 발생하지 않음 | `comments` 테이블 신설 |
| **파일 업로드** | 스토리지 인프라(Blob) 및 용량·보안 정책이 별도로 필요 | Vercel Blob 등 스토리지 연동 필요 |

> **원칙**: MVP 구현 중 위 항목을 위한 사전 작업(빈 테이블, 미사용 컬럼, 주석 처리된 코드)을 추가하지 않는다.
> CLAUDE.md의 "명세에 없는 기능 임의 추가 금지" 규칙을 따른다.

## 5. 사용자 시나리오

### 5.1 메인 시나리오: 할 일 등록 → 상태 이동 → 수정/삭제 → 완료 확인

```
 [1] 등록          [2] 상태 이동        [3] 수정/삭제       [4] 완료 확인
   │                  │                    │                   │
   ▼                  ▼                    ▼                   ▼
 Backlog  ──드래그──▶ TODO ──▶ In Progress ──모달 수정──▶  Done
                       │                                        │
                    startedAt                              completedAt
                    자동 기록                                자동 기록
```

#### 1단계: 할 일 등록

1. 사용자가 보드 상단의 **"새 티켓"** 버튼을 클릭한다
2. 생성 폼이 열린다
3. 제목을 입력한다 (필수, 1~200자)
4. 필요 시 설명, 우선순위, 시작예정일, 종료예정일을 입력한다
5. 생성 버튼을 클릭하면 폼이 닫히고 **Backlog 최상단**에 카드가 추가된다
   - 우선순위를 선택하지 않았다면 `MEDIUM`이 적용된다

> 관련 스토리: US-001, US-002 / 관련 기능: FR-001

#### 2단계: 상태 이동

1. 사용자가 Backlog의 카드를 잡아 **TODO 칼럼으로 드래그**한다
2. 드롭하는 즉시 카드가 이동한다 (낙관적 업데이트)
3. 서버에 `startedAt = 현재 시각`이 기록된다
4. 작업을 시작하면 다시 **In Progress**로 드래그한다
5. 같은 칼럼 안에서 드래그하면 우선 처리할 카드를 위로 올릴 수 있다

> 관련 스토리: US-003, US-005 / 관련 기능: FR-002, FR-007

#### 3단계: 수정 / 삭제

**수정**
1. 카드를 클릭하면 **상세 모달**이 열린다
2. 제목, 설명, 우선순위, 시작예정일, 종료예정일을 수정한다
3. 저장하면 보드에 즉시 반영된다

**삭제**
1. 상세 모달의 **삭제** 버튼을 클릭한다
2. 확인 다이얼로그가 표시된다
3. 확인하면 티켓이 영구 삭제되고 보드에서 사라진다

> 관련 스토리: US-007, US-008 / 관련 기능: FR-003, FR-004, FR-006

#### 4단계: 완료 확인

1. 작업을 마친 카드를 **Done 칼럼으로 드래그**한다
2. `completedAt = 현재 시각`이 기록되고 상태가 `DONE`이 된다
3. Done 칼럼에서 **최근 24시간 내 완료한 일**을 확인한다
4. 잘못 옮겼다면 다시 In Progress로 되돌린다 → `completedAt`이 초기화된다

> 관련 스토리: US-006 / 관련 기능: FR-005

### 5.2 보조 시나리오: 마감 초과 인지

1. 사용자가 보드를 연다
2. 종료예정일이 지났고 아직 Done이 아닌 카드에 **오버듀 경고 표시**가 나타난다
3. 사용자는 지연된 카드를 우선 처리하기 위해 상단으로 드래그한다

> 관련 스토리: US-004 / 관련 기능: FR-008

## 6. 핵심 기능 목록

REQUIREMENTS.md의 FR-001 ~ FR-008과 1:1 대응한다.

| ID | 기능 | 설명 | API | 관련 스토리 |
|----|------|------|-----|------------|
| **FR-001** | 티켓 생성 | 제목(필수)과 설명·우선순위·시작예정일·종료예정일(선택)로 티켓을 만든다. 항상 `BACKLOG` 상태로 생성되어 칼럼 최상단에 배치된다 | `POST /api/tickets` | US-001, US-002 |
| **FR-002** | 티켓 목록 조회 | 전체 티켓을 4개 칼럼별로 그룹화하여 반환한다. 칼럼 내 정렬은 `position` 오름차순이며, 각 티켓에 오버듀 여부가 파생 필드로 포함된다 | `GET /api/tickets` | US-003 |
| **FR-003** | 티켓 상세 조회 | 카드 클릭 시 상세 모달에 표시할 단일 티켓의 전체 정보를 반환한다 | `GET /api/tickets/:id` | US-007 |
| **FR-004** | 티켓 수정 | 제목·설명·우선순위·시작예정일·종료예정일을 부분 수정한다. 전송된 필드만 갱신되며 `null` 전송 시 해당 값을 삭제한다 | `PATCH /api/tickets/:id` | US-007 |
| **FR-005** | 티켓 완료 | Done 칼럼으로 이동시켜 완료 처리한다. `completedAt`에 현재 시각을 기록하고, Done에서 빠져나오면 `null`로 되돌린다 | `PATCH /api/tickets/:id/complete` | US-006 |
| **FR-006** | 티켓 삭제 | 확인 다이얼로그를 거쳐 티켓을 영구 삭제한다. MVP에서는 soft delete를 사용하지 않는다 | `DELETE /api/tickets/:id` | US-008 |
| **FR-007** | 상태/순서 변경 | 드래그앤드롭으로 칼럼 이동과 순서 변경을 처리한다. 상태와 `position`을 트랜잭션으로 동시 갱신하며, TODO 진입 시 `startedAt`을 기록한다. **Done으로의 이동은 FR-005를 사용한다** | `PATCH /api/tickets/reorder` | US-005 |
| **FR-008** | 오버듀 판정 | `dueDate < 오늘 AND status ≠ DONE` 조건을 만족하는 티켓에 경고 표시를 노출한다. DB에 저장하지 않고 조회 시 계산하는 파생 필드다 | 없음 (파생) | US-004 |

## 7. 기술 스택 요약

CLAUDE.md에 정의된 스택과 선정 이유다.

### 7.1 프레임워크 / 언어

| 구분 | 기술 | 선정 이유 |
|------|------|-----------|
| Framework | **Next.js 15 (App Router)** | 프론트엔드와 백엔드(Route Handlers)를 한 프로젝트에서 운영할 수 있어 단일 사용자 규모의 MVP에 서버를 따로 둘 필요가 없다. Vercel 배포와 네이티브로 통합된다 |
| Language | **TypeScript (strict)** | 티켓 상태·우선순위처럼 값이 고정된 도메인에서 컴파일 타임에 오류를 잡는다. `src/shared/`의 타입을 프론트·백엔드가 함께 사용하여 계약 불일치를 방지한다 |
| Frontend | **React 19** | Next.js 15의 기본 렌더링 계층이며, 칸반 보드처럼 상태에 따라 화면이 바뀌는 UI에 적합하다 |

### 7.2 UI / 상호작용

| 구분 | 기술 | 선정 이유 |
|------|------|-----------|
| Styling | **Tailwind CSS 4** | 유틸리티 클래스로 반응형 분기(모바일 1칼럼 → 데스크톱 다칼럼)를 컴포넌트 파일 안에서 처리한다. 별도 CSS 파일 관리 부담이 없다 |
| Drag & Drop | **@dnd-kit/core + @dnd-kit/sortable** | 칼럼 간 이동(`core`)과 칼럼 내 정렬(`sortable`)을 모두 지원한다. HTML5 Drag API와 달리 **터치와 키보드 조작을 기본 제공**하여 NFR-002(모바일 터치)와 NFR-003(접근성)을 함께 충족한다 |

### 7.3 데이터 계층

| 구분 | 기술 | 선정 이유 |
|------|------|-----------|
| ORM | **Drizzle ORM** | 스키마 정의에서 TypeScript 타입이 직접 추론되어 DB와 애플리케이션 타입이 어긋나지 않는다. 드래그앤드롭의 `position` 재계산에 필요한 트랜잭션을 지원한다 |
| DB | **Vercel Postgres (Neon)** | 서버리스 환경에 최적화된 커넥션 관리를 제공하여 Vercel Function 환경에서 커넥션 고갈이 발생하지 않는다. 관계형 DB이므로 `position` 기반 정렬과 트랜잭션 처리에 적합하다 |
| Validation | **Zod** | 하나의 스키마를 `src/shared/`에 두고 프론트엔드 폼 검증과 백엔드 요청 검증에 함께 사용한다(NFR-004 이중 검증). 스키마에서 타입을 추론할 수 있어 타입과 검증 규칙이 분리되지 않는다 |

### 7.4 품질 / 배포

| 구분 | 기술 | 선정 이유 |
|------|------|-----------|
| Testing | **Jest + React Testing Library** | CLAUDE.md의 TDD 사이클(Red → Green → Refactor)을 수행하기 위한 기본 러너다. RTL은 구현 세부가 아닌 사용자 관점의 동작을 검증하므로 인수 조건을 그대로 테스트로 옮길 수 있다 |
| Deployment | **Vercel** | git push만으로 자동 배포되고 PR별 프리뷰 환경이 생성된다. Next.js와 Vercel Postgres를 같은 플랫폼에서 운영하여 인프라 설정 부담이 없다(NFR-006) |

### 7.5 디렉토리 경계

```
app/api/       백엔드 진입점 — 요청 파싱 → 서비스 호출 → 응답 반환
src/server/    백엔드 로직 — services, db, middleware
src/client/    프론트엔드 로직 — components, hooks, api
src/shared/    공유 계약 — 타입, Zod 스키마, 상수
```

프론트엔드와 백엔드는 `src/shared/`를 통해서만 결합한다.
양쪽에 영향을 주는 변경은 `src/shared/`를 먼저 수정한 뒤 각각에 반영한다.

## 8. 와이어프레임 참고

### 8.1 레이아웃 원칙

**4칼럼 가로 배치** 보드 레이아웃을 채택한다 (NFR-002).

Backlog → TODO → In Progress → Done 네 칼럼을 같은 비중으로 좌에서 우로 나열한다.
칼럼 순서가 곧 작업의 진행 방향이므로, 사용자는 카드를 **오른쪽으로 밀어내는** 방향으로 작업한다.
각 칼럼은 독립적으로 세로 스크롤한다.

### 8.2 데스크톱 (1024px~)

```
┌────────────────────────────────────────────────────────────────────────────┐
│  Tika                                                       [ + 새 티켓 ]  │
├──────────────────┬──────────────────┬──────────────────┬───────────────────┤
│  BACKLOG     (7) │  TODO        (3) │ IN PROGRESS  (2) │  DONE         (4) │
│  ──────────────  │  ──────────────  │ ───────────────  │  ───────────────  │
│                  │                  │                  │                   │
│  ┌────────────┐  │  ┌────────────┐  │  ┌────────────┐  │  ┌────────────┐   │
│  │ PRD 초안   │  │  │ API 설계   │  │  │ 보드 구현  │  │  │ 스키마     │   │
│  │ [MEDIUM]   │  │  │ [HIGH]     │  │  │ [HIGH]     │  │  │ [LOW]      │   │
│  │ ~09/05     │  │  │ ~09/03     │  │  │ ~09/06     │  │  │ ✓ 완료     │   │
│  └────────────┘  │  └────────────┘  │  └────────────┘  │  └────────────┘   │
│                  │                  │                  │                   │
│  ┌────────────┐  │  ┌────────────┐  │  ┌────────────┐  │  ┌────────────┐   │
│  │ 테스트작성 │  │  │ 모달 UI    │  │  │ DnD 연동   │  │  │ 초기 설정  │   │
│  │ [LOW]      │  │  │ [MEDIUM]   │  │  │ [MEDIUM]   │  │  │ [MEDIUM]   │   │
│  │ ⚠ 09/01    │  │  │ ~09/04     │  │  │ ~09/07     │  │  │ ✓ 완료     │   │
│  └────────────┘  │  └────────────┘  │  └────────────┘  │  └────────────┘   │
│                  │                  │                  │                   │
│  ┌────────────┐  │  ┌────────────┐  │                  │  · 24시간 이내    │
│  │ 배포 파이프│  │  │ 오버듀뱃지 │  │                  │    완료분만 표시  │
│  │ [MEDIUM]   │  │  │ [LOW]      │  │                  │                   │
│  └────────────┘  │  └────────────┘  │                  │                   │
│                  │                  │                  │                   │
└──────────────────┴──────────────────┴──────────────────┴───────────────────┘
   └──────────────────── 진행 방향: 좌 → 우 (역방향 이동도 허용) ─────────▶
```

**구성 요소**

| 영역 | 내용 |
|------|------|
| 헤더 | 제품명, "새 티켓" 생성 버튼 |
| 보드 | 4칼럼을 동일 너비로 가로 배치. 칼럼별 독립 세로 스크롤 |
| 칼럼 헤더 | 칼럼명 + 카드 수 |
| 카드 | 제목, 우선순위 뱃지, 종료예정일(또는 완료 표시), 오버듀 경고 |

### 8.3 카드 구성

```
┌──────────────────────────────┐
│  테스트 케이스 작성          │  ← 제목 (최대 2줄, 말줄임)
│                              │
│  [ HIGH ]        ⚠ 09/01     │  ← 우선순위 뱃지 / 종료예정일
└──────────────────────────────┘
     │                  │
     │                  └─ 오버듀 시 ⚠ 경고 표시 (FR-008)
     └─ LOW 회색 / MEDIUM 파란색 / HIGH 빨간색
```

### 8.4 티켓 상세 모달

카드 클릭 시 열린다. 수정과 삭제를 모두 이 모달에서 처리한다.

```
┌────────────────────────────────────────────┐
│  티켓 상세                            [ X ] │
├────────────────────────────────────────────┤
│  제목    [ 테스트 케이스 작성            ]  │
│                                            │
│  설명    ┌──────────────────────────────┐  │
│          │ FR-001~008 대응 테스트 작성  │  │
│          └──────────────────────────────┘  │
│                                            │
│  우선순위  ( LOW )  ( MEDIUM )  ( ●HIGH )  │
│                                            │
│  시작예정일  [ 2026-09-01 ]                │
│  종료예정일  [ 2026-09-05 ]                │
│                                            │
│  ─────────────────────────────────────     │
│  시작일    2026-09-02 10:14  (자동)        │
│  종료일    -                  (자동)        │
│  ─────────────────────────────────────     │
│                                            │
│  [ 삭제 ]                  [ 취소 ] [ 저장 ]│
└────────────────────────────────────────────┘
```

- 시작예정일/종료예정일은 **입력 가능**하다
- 시작일/종료일은 칼럼 이동으로 자동 기록되므로 **읽기 전용**으로 표시한다
- 삭제 버튼은 확인 다이얼로그를 거친다
